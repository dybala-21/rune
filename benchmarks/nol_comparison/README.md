# NOL 숙소 비교: 실제 웹 E2E

한 번의 요청이 Rune 웹 API → 실제 모델 → Rune 소유 Chromium → 실제 NOL 웹 → 근거 있는 비교 결과까지 이어지는지 검사한다. 사이트 응답, 검색 결과, 가격, 모델 호출은 대체하지 않는다. 별도 계정 로그인이나 예약·결제는 하지 않는다.

## 실행

저장소 루트에서 기존 개발·브라우저 의존성을 설치한 환경을 사용한다. 호출할 제공사의 키와 모델을 먼저 설정한다.

```bash
.venv/bin/python -m pytest tests/e2e/test_live_nol.py \
  --run-live --live-provider anthropic --live-model claude-opus-5 \
  --decision-backend connected --live-repeat 1 \
  --nol-browser visible --nol-destination sapporo --nol-request short \
  --live-report-dir output/nol-e2e -q --tb=short
```

모델 이름은 계정에서 사용 가능한 것으로 변경할 수 있다. 기본 실행당 모델 비용 상한 $5, 최대 모델 요청 70회, 에이전트 실행 600초, 토큰 예산 150만 개를 적용한다. 알려진 단가가 없으면 비용 제한을 해제하지 않고 호출 전에 실패한다. 가격 추정·제공사 사용량의 한계는 기존 request budget과 같다. 웹사이트·호스트 비용은 이 토큰 예산에 포함되지 않는다.

기본 시나리오는 실행일의 한국 시간 기준 14일 뒤 체크인, 다음 날 체크아웃, 서울, 성인 2명·객실 1개, 전체 숙박기간의 **표시 객실료** 20만 원 이하의 서로 다른 숙소 3곳이다. 별도 현장 세금은 원문으로 분리하며 최종 결제 총액으로 단정하지 않는다. 계산한 절대 날짜를 요청과 보고서에 기록한다. 요청 횟수는 하나이며 추가 답변·자동 승인으로 테스트를 통과시키지 않는다.

해외 경로는 `--nol-destination sapporo`로 별도 실행한다. 현재 기본 요청 형식인 `--nol-request short`는 숙소 ID·시작 URL·도구 이름·JSON 스키마 없이 도시·일정·인원·예산·비교 항목만 요청한다. 이전의 긴 절차 지시는 `--nol-request guided`로 재현하며, 이 형식의 해외 시나리오만 사용자가 제공한 `TDP-125731` 상세에서 시작한다. 날짜·인원·가격 상한은 동일하다. 해외 성공이 국내 성공을 의미하지 않는다. `--nol-browser` 기본값은 `managed`(headless)이며 `visible`은 개인 프로필을 사용하지 않는 새 표시 브라우저다.

## 판정과 증거

- 반환 JSON이 명시된 비교 스키마를 만족해야 한다.
- 각 후보는 요청한 국내/해외 시나리오에 맞는 실제 NOL 숙소 상세 URL을 가져야 한다. 같은 숙소에 서로 다른 query를 붙여 개수를 채울 수 없다.
- 날짜·인원·위치·객실 가격·취소·가격 적용 조건 인용문을 모델 외부에서 수집한 페이지 텍스트와 대조한다. 서로 다른 날짜의 화면을 합쳐 증거로 삼을 수 없다.
- 요청 가격 상한, 후보 개수, 중복, 날짜의 연도까지 검사한다. 부분 결과·확인 불가 조건은 성공으로 집계하지 않는다.
- HTTP 오류, 사용자 개입, 비JSON 응답, 후보 부족은 실패다. 외부 사이트 오류를 skip/xfail로 바꾸지 않는다.
- 보고서는 commit/content hash, 실제 모델·설정·비용·도구 호출, 원본 요청·응답, 검증 실패 이유와 수집한 화면을 포함한다. 실제 웹의 변동 때문에 재실행 결과는 달라질 수 있다.

일반 보고서는 `<report-dir>/<batch-id>/<trial-id>.json`, 화면과 페이지 텍스트는 `<report-dir>/nol-evidence-<id>/`에 저장한다. 공개 비로그인 화면이라도 네트워크 IP 등 진단 정보가 포함될 수 있으므로 그대로 공개 커밋하지 않는다.

인용 대조는 출처·요청 조건의 일관성 검사다. 임의의 취소 조항 의미, 쿠폰 자격, 숨은 수수료, 실제 결제 가능 여부까지 증명하지 않는다. 첫 성공 시에도 객실별 가격 적용 조건을 원본 화면과 사람이 대조해야 하며, 예약 E2E는 별도 작업이다.

## 구현 근거와 첫 실험

공식 [NOL 홈](https://nol.yanolja.com/)과 [호텔 카테고리](https://nol.yanolja.com/sub-home/hotel?verticalCategory=LOCAL_ACCOMMODATION&verticalSubCategory=HOTEL)를 확인했다. 검색엔진에서 읽히는 공개 콘텐츠와 이 호스트의 실제 브라우저 접근 가능성은 다르므로 웹 검색 결과를 실제 브라우저 성공으로 간주하지 않는다.

2026-11-01 첫 실모델 실행은 NOL HTTP 403으로 후보 0개, E2E 실패였다. 이 과정에서 탐색 도구가 HTTP 오류를 성공으로 반환하는 문제를 확인했다. Playwright의 `goto`는 404/500 등의 응답에 자동으로 예외를 발생시키지 않으므로 반환 status를 검사하도록 수정했다. 응답 화면은 계속 읽을 수 있지만 요청 콘텐츠를 가져왔다고 표시하지 않는다. [Playwright 공식 goto 문서](https://playwright.dev/python/docs/api/class-page#page-goto)

실제 지원 상태는 아래 최신 실행 결과를 기준으로 판단한다. 숙소 비교가 실제로 성공했다고 발표하려면 이 테스트의 성공 보고서와 객실별 수동 대조가 필요하다.

### 국내 실험: 2026-11-01

기준 main `7bf5ff3`, 브랜치 `codex/nol-comparison-e2e`. 요청은 서울, 2026-11-15~16, 성인 2명·객실 1개, 20만 원 이하 3곳이다. 기존 설정의 Anthropic `claude-opus-5`를 사용했고 별도 decision backend는 사용하지 않았다.

### 사용자 링크를 반영한 경로별 재검증

사용자가 정상 접속된다고 알려준 해외 상세 `https://nol.yanolja.com/stay/overseas/TDP-125731`를 같은 새 visible Chromium에서 국내 상세와 비교했다. 이 진단에는 LLM을 사용하지 않았다.

- 해외 상세: HTTP 200. 사용자 링크의 11월 1~2일과 비교 시나리오의 11월 15~16일 모두 열림. 후자는 객실 1개·성인 2명 및 객실 가격까지 로드됨.
- 국내 상세 `/stay/domestic/3001564`: HTTP 403. 기존 Rune 실행에서도 국내 상세 3곳이 403을 반환함.
- 해외 화면에는 쿠폰 조건 및 현장 숙박세가 있으므로 표시 최저가를 전체 비용으로 단정할 수 없음.
- 증거: `output/nol-route-diagnostic/`의 응답·화면·객실 텍스트.

따라서 **NOL 전체가 접속 불가하다는 판단은 잘못이다**. 확인된 것은 실행 환경과 국내/해외 경로별 응답 차이이며, 차단의 원인은 확정하지 않았다. 해외 접속 진단만으로 한 번 요청한 비교 작업의 성공을 주장하지 않는다.

### 회귀 검사와 남은 범위

단위 96개와 실제 Chromium 통합 55개가 통과했고 변경 파일 Ruff 및 `git diff --check`가 통과했다. 검증기는 날짜·가격 등의 인용 출처를 검사하지만 인원 숫자가 실제 성인 항목인지, 모든 추가 세금이 합산됐는지, 각 취소 조건이 선택 객실에 귀속되는지까지 의미적으로 증명하지 않는다.

이 단계의 변경은 실제 실행 검증 harness와 실행 중 발견된 브라우저 도구 오류 수정이었다. 전용 NOL 커넥터, 예약·결제, 사용자 Chrome 인증 연결, iOS 앱 조작을 구현한 것은 아니다. 검색/필터 작업을 browser `edit`로 분류하는 문제는 아래 후속 구현에서 개선했다.

### 해외 실모델 실행 결과

보고서: `output/nol-e2e-overseas/64734c5635da43c3a03f4255bb87707c/f70993c8c4494c1f8a88033928d4212f.json`.

- 요청 1회, 중간 사용자 개입 없음, 실제 visible 브라우저 사용.
- 281.047초, 모델 35회·도구 33회(실패 8회), 1,442,725 tokens, 추정 $3.50585.
- 해외 숙소 2곳(TDP-125731, TDP-124312)의 상세와 객실 목록을 실제로 열었고 HTTP 오류는 없었다.
- 세 번째 숙소까지 완료하지 못하고 토큰 예산 소진. 세금/쿠폰 적용 조건도 미확인 상태여서 **E2E 실패**다. 일부 가격을 읽었다는 사실을 비교 완료로 집계하지 않는다.
- 실행 로그 `text`에는 2곳의 부분 JSON이 있지만, 최종 `answer`는 저장 결과 확인 실패라는 일반 문구다. 읽기 작업을 `browser_effect=edit`로 분류한 것이 이 잘못된 종료 안내에 영향을 주었다. 검증기는 최종 답변을 평가하므로 `Invalid comparison JSON`, `offers_checked=0`을 기록했다.
- 동일 이름의 객실 상세 버튼에 대해 유효한 핸들이 없는 ref가 제공되어 3차례 동작이 거부됐다. 안전 검증을 우회하지 않았으며 반복 관찰만으로 해결되지 않는 참조 제공 문제가 남아 있다.
- `browser_find`가 `div.!whitespace-normal`이라는 잘못된 선택자를 반환해 후속 추출이 실패했다. 실행 후 `CSS.escape`로 클래스/ID를 이스케이프하도록 수정했다. [CSS.escape 문서](https://developer.mozilla.org/en-US/docs/Web/API/CSS/escape_static)
- 해외 객실 목록의 `/list` URL을 같은 숙소의 상세 근거로 허용하고, 같은 숙소를 중복 집계하지 않도록 했다. 요청 도시의 명시적 영문 표기(Sapporo/Seoul)도 주소 증거로 허용한다.

CSS 수정 후 실제 Rune `browser_open → browser_find → browser_extract`를 같은 해외 숙소에서 직접 호출해 HTTP 200 및 취소 조건 추출 성공을 확인했다(LLM 미사용, `output/nol-route-diagnostic/selector-fix.json`). 이는 도구 수정 검증이며 3곳 비교 E2E 성공이 아니다.

해외 실모델 실행 당시 `source_unchanged=true`다. 이후 CSS 선택자와 검증기를 보완했으므로 위 보고서는 그 수정 후 전체 E2E 성공 근거가 아니다. 실제 모델을 호출한 국내·해외 5회 합계는 약 $9.44다.

남은 우선순위는 (1) 중복 라벨에 대한 명확한 DOM 참조 제공, (2) 검색·조건 조회를 저장 작업과 구분하는 분류 및 완료 안내, (3) 불필요한 재관찰과 대량 출력 감소, (4) 같은 조건으로 3곳 비교 재검증이다. 국내 HTTP 403은 이와 별개의 미해결 접근 문제다.

### 연구 메모: 2026-11-01

후속 구현은 [연구 근거와 실험 계획](research.json)을 기준으로 한다. 이 연구 차례에는 제품 코드를 변경하지 않았다. 기존 Rune 연구 실행 경로로 주요 3개 자료를 추가 대조했으며, 공개 원문·코드·실행 로그를 직접 확인한 내용과 가설을 분리했다.

- 중복 이름의 버튼에 핸들을 연결하지 않으면서 ref를 노출하는 구현 불일치가 확인됐다. [BrowserGym](https://arxiv.org/html/2412.05467v4)은 DOM/AXTree와 동작을 요소별 ID로 연결한다. 노드 교체 후 옛 참조를 거부하는 기존 보호는 유지해야 한다.
- [OpenAI 공개 가이드](https://developers.openai.com/api/docs/guides/tools-computer-use)는 코드 실행과 구조화된 컴퓨터 동작을 모두 다룬다. 화면만 클릭하는 구현이라고 단정하지 않는다. 공개 예제는 제품 내부 전체 구현이나 NOL 성공률의 근거가 아니다.
- [OpenAI 컨텍스트 예제](https://developers.openai.com/cookbook/examples/agents_sdk/building_reliable_agents_memory_compaction)는 현재 작업 문맥·재사용 메모리·검토 가능한 결과물을 구분한다. Rune에도 이미 압축/복구가 있으므로 숙소별 증거 보존과 측정 누락을 먼저 확인한다.
- [Odysseys](https://arxiv.org/html/2604.24964v1)의 200단계 실험은 예산 증가가 일부 모델에 도움이 됨을 보고한다. 예산 증가가 항상 무익하거나 항상 충분하다고 주장하지 않는다. 사전공개 연구이며 NOL에 효과를 옮겨 단정할 수 없다.

독립 E2E 관찰자는 실제 클릭 전 카드와 클릭 후 팝업 DOM을 별도로 수집한다. 생산 수집기의 ‘같은 요금’ 주장을 그대로 신뢰하지 않고 현재 가격·선택 카드·전체 정책 영역·정확한 인용을 검증한다. DOM 구조의 연결 검증이며 임의 정책의 모든 의미, 개인별 할인 자격, 실제 결제/예약 가능성의 증명은 아니다. 현재 어댑터는 관측한 NOL 해외숙소 데스크톱 DOM에 한정된다.

실험 중 두 실행 경로 문제도 수정했다. 웹 조회로 분류된 요청에서 증거 수집 도구가 누락돼 검색으로도 찾을 수 없던 문제를 고쳤다. 또 새 CSV 자료 수집을 기존 표 집계로 오인하지 않도록 의미 분류 지침을 명확히 하고, 큰 도구 목록에서도 브라우저 진입 도구를 바로 제공한다. 기존 집계 검증을 끄거나 자연어 키워드 규칙을 추가하지 않았다.

[Meta의 Muse 공식 설계 사례](https://introducing.muse.ai/)에는 상품 탐색·장바구니, 식당 예약, 학교 웹사이트/메일에서 가족 일정으로 옮기기, 문서·대시보드 생성 등이 있다. 이번에는 **Rune으로 상품 비교→CSV, 공식 일정 추출→CSV를 재현**했다. Muse 자체를 실행한 A/B 비교가 아니며 구매, 식당 예약, 인증, 실제 캘린더 쓰기, 백그라운드 감시는 평가하지 않았다.

### 완료 판정 회귀 수정: 2026-11-03

PR #120 검토에서 두 문제를 재현했다. 사용자가 숙소 3곳을 요청해도 수집기가 자체 조건을
1곳으로 낮추면 완료로 인정했고, 최종 결과에 인용하지 않은 오래된 소스가 남아 있으면
신선한 결과까지 만료로 판정했다.

첫 문제는 기존 요청 분류 응답에 `stay_query`를 추가해 처리한다. 수집 전에 도시·일정·인원·객실 수·
숙소 수·표시 금액 상한을 추출하고 현재 요청에 연결한다. `begin`에서 다른 조건을 거부하고,
완료 시에도 조건 해시와 요청한 숙소 수를 재검증한다. 연결 모델의 기존 분류 호출에 포함하며,
선택형 라우터는 NOL 비교를 감지하면 기존 fallback 경로로 조건 추출을 넘긴다.
`web` 조회와 `browser` 경로 모두 지원한다. 조건이 누락되거나 요청이 바뀌었으면 이전 조건으로
완료 처리하지 않는다. 현재 스키마로 표현할 수 없는 추가 요구는 확인이 필요하다.

이는 [OWASP Input Validation Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)의
구조 검증과 업무 맥락에 맞는 의미 검증을 구분하는 원칙을 적용한 것이다. 요청 조건 추출 자체는
모델의 의미 해석이므로, 모델이 처음부터 잘못 해석한 조건까지 결정적으로 증명하는 검사는 아니다.
이 회귀는 실행 중 조건 축소와 다른 요청의 조건 재사용을 차단한다.

두 번째 문제는 반환할 숙소·객실의 `evidence_refs`에서 실제 참조한 소스만 만료 계산에 사용하는 것으로
수정한다. 사용하지 않은 과거 관측은 감사용으로 보존하며, 인용한 소스가 오래된 경우에는 여전히
완료를 거부한다.

`tests/unit/test_stay_contract.py`는 조건 변경의 실행 전 거부, 누락·재사용 조건의 거부,
최종 결과의 소스 유효기간, 실제 에이전트 루프의 정상·예산 종료 경로를 검증한다.
숙소 1곳의 완전한 증거로 3곳 요청을 완료할 수 없고, 3곳의 유효한 증거로는 완료할 수 있는지
함께 검사한다. 라우팅 회귀는 연결 모델과 선택형 라우터 fallback을 검사한다.
모델 전송은 테스트 대역을 사용하며 이번 수정 검증은 실제 NOL 재실행이나 로그인·예약·결제 검증이 아니다.
